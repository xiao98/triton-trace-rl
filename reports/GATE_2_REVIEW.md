## 阻塞问题：中转站支撑不了正式评测

1. **限流。** 试点总共只发了约 100 次调用，就收到 `Claude Max rate limit reached`，`retry_after` 约 4.3 小时。
   正式评测是训练集 1440 次 + 留出集 960 次调用，按这个限额跑不完。
2. **`claude-fable-5-2` 不可用**（中转站返回"需要用量额度"），试点用的是 `claude-opus-5-5`。
3. **它不是直连 API。** 报错信息显示中转站背后是 Claude Code 订阅，会给每次请求加约 850 token 的前缀。
   系统提示词确实生效（实测过），但评测对象严格说是"经中转站包装的 Opus 5.5"，写报告时需要注明。
4. 同一道题的并发相同请求会冲突（`already has an active SDK writer`），已改为同题串行绕开。

需要你决定：换成 Anthropic 官方 API key（最干净，约 170 美元跑完训练集 + 留出集，按上面的名义估计）；
或者缩小规模（少题、少方式、预算从 4 降到 2）；或者接受用中转站慢慢跑（要跑很多天，且要在报告里注明）。

## 试点暴露并已修复的问题

1. **评测器爆显存（我的设计问题）。** `cumprod` 单个输入 4 GB，沙箱原先把 3 个种子的输入和参考输出一次全放进
   显存。已改为逐个种子生成、用完即释放，并把输出比对改成分块。代价是可信的参考代码现在夹在候选代码调用
   之间运行；这段时间父进程会暂停候选的计时。
2. **显存不够测速时如实标记。** 测速需要至少 2 组候选没见过的输入（否则回放缓存能蒙混过关）。放不下时结果
   记为"正确、无加速比"并写明原因，不估算。`Max_Pooling_3D` 在 L4 上就是这种情况。
3. **多轮方式白白浪费提交次数。** 模型收到"你的提交是正确的"之后经常回一段文字而不是代码，被判成语法错误，
   占掉一次提交（多轮两个方式里 8 次 `static_reject` 有 6 次是这个原因）。已让每条反馈都明确要求"回复完整
   文件"。**这个修复是在试点之后做的，没有重跑验证**，上表里的多轮数字因此偏低。
4. `cumprod` 的修复（分块比对）也**没有在 GPU 上重跑验证**，被限流打断了。它的 12 次提交记录已移到
   `pilot_train5_v2_invalid_cumprod_harness_oom/`，没有计入上表。

## 需要你留意的观察

- **守卫可能偏严。** 有 2 次提交因 `.item()`、1 次因 `torch.float16` 被静态拒绝。这是按现有规则判的（读张量的值
  可以用来做按值缓存作弊），但会压低正确率。要不要放宽请你定。
- **Level 2 的"算错"多数误差在 1e-3 到 1e-2**，高于 1e-4 的容差。两道题都带 BatchNorm，我怀疑和 BN 的训练 /
  推理模式或浮点累加顺序有关，**没有查证**。模型在这两道题上也都拿到过正确解，所以不是做不对。
- 没有出现运行时作弊判定，也没有拒答，24 + 16 次调用全部由 `claude-opus-5-5` 作答。
